## Oracle separation

`upstream-vectors.txt` was generated by compiling the pinned upstream nested classes with only their Telegram protocol serialization methods removed. It does not execute App Matrix's `ToneCurves` or `CurveMap`.

Eight profiles cover identity, lifted tone, inverted tone, alternating extrema, monotone knots with a plateau, fractional levels, all-black, and all-white. Every record contains:

1. Profile name
2. Five control points, percent units
3. All 200 sampled values as exact IEEE-754 float hexadecimal bits
4. Drawing-path float count
5. SHA-256 of the complete drawing path, with each float serialized little-endian

The samples correspond to `t = .01, .03, ... .99` on each of four segments. They are **not** 200 equally spaced x-coordinates and do not include the endpoint knots. The drawing path has 804 floats and includes the extra x endpoints −.001 and 1.001. Catmull–Rom overshoot is clamped to [0,1]; monotone input knots do not guarantee a monotone output spline. The exact identity operation therefore relies on the upstream default bypass.

`cpu-vectors.txt` uses those upstream-generated, truncating UNORM8 tables but computes color conversion independently: double-precision chroma/sector HSL equations instead of the production hue helper. Its 250 input/output ARGB pairs cover ten four-channel profiles, RGB/CMY primaries, black/white/grays, highly saturated colors, near-black/near-white saturation attenuation, arbitrary colors, and transparent/partial-alpha inputs. Each record contains comma-separated luminance/red/green/blue profile names, input ARGB, and expected output ARGB.

The CPU contract intentionally uses clamped `floor(value * 200)` lookup. Upstream OpenGL uses `GL_LINEAR` and samples texture coordinates at `index/200`, so these CPU fixtures do **not** claim pixel identity with Telegram's GPU. They preserve the shader's order: RGB → HSL, attenuate saturation using **original** lightness, map lightness, HSL → RGB, then map R/G/B. Original alpha is preserved. No exposure, contrast, other Telegram effects, or GPU precision behavior is included.

## Reproduce without using product code

Provide a local, complete copy of the pinned `PhotoFilterView.java` and a JDK 17+:

```sh
python3 shared/core/src/test/resources/telegram-curves/regenerate.py \
  /path/to/pinned/PhotoFilterView.java \
  --java-home /path/to/jdk \
  --output /tmp/regenerated-telegram-curves
diff shared/core/src/test/resources/telegram-curves/upstream-vectors.txt /tmp/regenerated-telegram-curves/upstream-vectors.txt
diff shared/core/src/test/resources/telegram-curves/cpu-vectors.txt /tmp/regenerated-telegram-curves/cpu-vectors.txt
```

The reproduction tool verifies the exact Git blob hash, performs no network access, never imports the product implementations, and uses a temporary directory for compiled oracle classes. Compare regenerated files before intentionally replacing fixtures.

## Test boundaries

`TelegramCurveParityTest` is pure Java/JUnit 4. It also verifies RGBA byte order and truncation, cache/save/restore behavior, exact default bypass, channel/alpha handling, immutable render snapshots, explicit stale-cache refresh, invalid control values and array mapping.

These tests cannot verify Android touch dispatch, accessibility traversal, view rendering, bitmap/JPEG integration, or real GPU output. Those require Android/device tests. A mathematical parity pass is not a product UI or export acceptance pass.
